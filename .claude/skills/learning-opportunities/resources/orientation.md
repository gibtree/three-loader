# Repo Orientation: three-loader

> Generated by /orient:orient. Re-run to update.

## One-line purpose
`@pnext/three-loader` is a TypeScript library that streams Potree point cloud data into Three.js scenes using progressive, camera-aware Level-of-Detail loading — and optionally renders Gaussian Splats from the same data.

## Primary language(s)
TypeScript (compiled via Webpack + ts-loader; tested with Jest + Babel)

## Pipeline / workflow stages
1. **Load metadata** — `Potree.loadPointCloud()` calls either `loadPOC` (v1) or `loadOctree` (v2), which fetches a JSON manifest (`cloud.js` or `metadata.json`) describing the octree structure and point attributes.
2. **Parse hierarchy** — `OctreeLoader` and `NodeLoader` parse the binary hierarchy file (`hierarchy.bin`) to build the in-memory octree of `OctreeGeometryNode` objects (CPU-side, not yet on GPU).
3. **Priority-queue visibility update** — Each animation frame, `Potree.updateVisibility()` computes per-cloud frustums in object space and runs a max-heap priority queue (screen-pixel-radius weighted) over the octree to select which nodes should be visible within the `pointBudget`.
4. **Async node loading** — Nodes selected by the priority queue but not yet loaded have their `.load()` called; this dispatches to a `WorkerPool` (web workers) to decode binary point data off the main thread.
5. **GPU upload** — When a geometry node's data arrives (`.loaded = true`), `PointCloudOctree.toTreeNode()` wraps it in a Three.js `Points` object, attaching the shared `PointCloudMaterial`, and adds it to the scene graph.
6. **Material + splats update** — `PointCloudMaterial.updateMaterial()` refreshes uniforms. If nodes carry `COVARIANCE0` attributes, `SplatsMesh.update()` + `sortSplats()` handle Gaussian Splatting via a sort worker and instanced geometry.
7. **Memory management** — `LRU.freeMemory()` evicts the least-recently-touched nodes when total loaded points exceed `pointBudget * memoryScale`, keeping GPU memory bounded.

## Key files
- `src/potree.ts` — The `Potree` class: entry point for loading and the per-frame `updatePointClouds()` loop; orchestrates visibility, loading, and LRU eviction.
- `src/point-cloud-octree.ts` — `PointCloudOctree`: the Three.js `Object3D` that represents a loaded cloud; owns the material, splats mesh, and node upgrade logic (`toTreeNode`).
- `src/types.ts` — Core interfaces (`IPointCloudTreeNode`, `IPotree`, `IVisibilityUpdateResult`, `PCOGeometry`); the contract between all major components.
- `src/loading2/octree-loader.ts` — V2 loader: parses metadata, builds `OctreeGeometry`, resolves encoding (DEFAULT vs GLTF vs GLTF splats), and starts root-node loading.
- `src/loading2/decoder.ts` / `gltf-decoder.ts` / `gltf-splats-decoder.ts` — Pluggable decoders dispatched by `NodeLoader`; each decoder has a matching web worker file.
- `src/materials/point-cloud-material.ts` — A `RawShaderMaterial` with GLSL3 shaders; supports many coloring modes (height, intensity, classification, RGB), clip boxes, and point shape.
- `src/utils/lru.ts` — Doubly-linked-list LRU cache that tracks loaded nodes by point count and evicts to stay within budget.
- `src/splats-mesh.ts` — Gaussian Splatting renderer: pre-allocates GPU textures for positions/covariances/harmonics, sorts splats by depth each frame using a WASM sort worker.

## Core concepts

**Octree LOD**: Point clouds are spatially partitioned into an octree. Each node covers a bounding box region and may have up to 8 children at half the spacing. The root is always loaded; children are loaded on demand based on screen coverage, so distant or small regions stay low-resolution.

**Geometry node vs tree node**: There are two life-cycle states for a node. An `IPointCloudGeometryNode` (geometry node) holds metadata and, once loaded, raw `BufferGeometry` on the CPU. A `PointCloudOctreeNode` (tree node) has been promoted — it wraps a Three.js `Points` object that lives in the scene graph and is on the GPU. The transition happens in `PointCloudOctree.toTreeNode()`.

**Point budget + LRU eviction**: `Potree.pointBudget` is a global cap on visible points. The visibility algorithm stops adding nodes once the budget is exceeded. Simultaneously, `LRU.freeMemory()` disposes subtrees of nodes that haven't been seen recently, freeing GPU memory.

**Loader versions (v1 / v2)**: The `Potree` constructor accepts `'v1'` (default, for original Potree converter output with `cloud.js`) or `'v2'` (for PotreeConverter 2 output with `metadata.json`). V2 also supports `GLTF` encoding for datasets from tools like Pix4D. Choosing the wrong version will fail silently at load time.

**Gaussian Splatting**: If a loaded node's `BufferGeometry` has a `COVARIANCE0` attribute, the cloud switches to splat rendering. A `SplatsMesh` is created that pre-allocates packed GPU textures (position+color, covariance, optional spherical harmonics). Each frame splats are depth-sorted by a WASM worker and rendered as instanced quads.

## Common gotchas

- **`updatePointClouds()` must be called every frame** — loading is fully streaming. Calling `loadPointCloud()` only starts the process; nodes continue to load and upload to the GPU frame by frame. Skipping `updatePointClouds()` means nothing new ever appears, even after the initial load resolves. See `potree.ts:93`.

- **`exceededMaxLoadsToGPU` means call again** — `IVisibilityUpdateResult.exceededMaxLoadsToGPU` is `true` when nodes are decoded and ready but weren't uploaded this frame (the `MAX_LOADS_TO_GPU` cap). The caller should call `updatePointClouds()` again on the next frame — the data is waiting. Ignoring this flag causes visible "holes" that never fill. See `types.ts:44`.

- **Wrong version silently loads nothing** — If a `cloud.js` dataset is loaded with `new Potree('v2')`, the fetch will 404 or return unexpected JSON and the root node will never load. No error is surfaced to the caller. Always match the `Potree` version to the dataset format (V1 = `cloud.js`, V2 = `metadata.json`).
